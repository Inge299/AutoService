# Контракт серверного пилота

## Материалы визита в кабинете мастерской

`GET /v1/visits/:id/media` требует staff-сессию и проверяет принадлежность визита
мастерской пользователя. Для чужого или отсутствующего визита возвращает `404`.
Возвращает все материалы визита со статусом `VERIFIED` или `READY`, включая фото,
видео и голос, привязанные к находке либо непосредственно к визиту. Формат элемента:
`{ id, findingId, kind, mimeType, url, expiresInSeconds }`. Ссылки на закрытое S3
действуют 15 минут; ответ имеет `Cache-Control: private, no-store`. Имена object key
и серверные ключи не передаются. Для обновления ссылок кабинет повторно запрашивает
страницу. Непроверенные файлы не выдаются как готовые материалы.

## Реализовано

Сервер — источник истины для визитов, находок и медиа. Android создаёт и меняет визит
только через API, а Room использует как кэш отображения и устойчивую очередь медиа до
серверного подтверждения SHA-256.

## Следующий этап

| Операция | Планируемый path | Статус |
|---|---|---|
| Открыть клиентскую страницу | `GET /a/{token}` | Реализовано веб-слоем |
| Отправить SMS/сообщение | `POST /v1/approval-links/{id}/send-message` | Не реализовано |

Создание согласования требует `operationId`, 256-битный URL-safe токен и список
подтверждённых материалов находки. Пустой список допустим только при явном
`descriptionOnly: true`; Android для обычного согласования такой режим не использует.
При повторе с теми же `operationId` и токеном API
возвращает ту же ссылку; в БД хранится только хеш токена.

Материал проходит две стадии: загрузочный объект принимает presigned PUT, затем worker
проверяет SHA-256 и публикует отдельный неизменяемый объект. Для `VERIFIED`/`READY`
API не выдаёт новый upload URL и не принимает binary fallback. Любой материал, на который
ссылается опубликованное согласование или отчёт, нельзя удалить.

Сотрудник синхронизирует находку только в состояниях `DRAFT` и
`READY_FOR_APPROVAL`. Статусы `SENT_TO_CUSTOMER`, `APPROVED`, `DECLINED`,
`DEFERRED` и `CALL_REQUESTED` защищены от staff API: их меняет только создание/отзыв
ссылки либо публичный endpoint решения клиента.

После решения клиента мастер может вызвать `POST /v1/findings/{id}/complete`. Сервер
принимает переход только `APPROVED → COMPLETED`, пока визит не завершён или отменён;
синхронизация находки не может подменить этот статус.

Черновик отчёта содержит выполненные работы, рекомендации и дату следующего визита.
При публикации сервер фиксирует независимую версию со снимком данных визита, находок и
подтверждённых материалов, закрывает визит и возвращает URL `/r/{token}`. Как и для
согласования, токен остаётся только у вызывающего клиента, а в БД хранится его хеш.
Отзыв ссылки возвращает отчёт в черновик и разрешает выпуск следующей версии.

Завершённый или отменённый визит нельзя изменять общим `PUT /v1/visits/{id}`:
сервер отвечает `409 visit_closed`. Этот же ответ возвращается при создании или
изменении находки и сохранении неопубликованного черновика отчёта в закрытом визите.
Для уже опубликованного отчёта сохраняется ответ `409 report_already_published`,
нужный для восстановления идемпотентной публикации Android. Перенос существующей
находки между визитами запрещён (`409 finding_visit_mismatch`). Переход в `COMPLETED`
через общий PUT, включая создание визита, запрещён (`409 visit_status_managed_by_report`);
для исправления опубликованного визита нужно отозвать его отчёт и выпустить новую версию.

В сохранении визита телефон приводится к E.164 тем же правилом, что и при авторизации;
неверный телефон и отсутствие одновременно автомобиля и госномера дают `400 invalid_request`.
Дата следующего визита проверяется при сохранении черновика и повторно при публикации:
прошедший календарный день по Москве отклоняется с `400 next_visit_date_in_past`.
Сегодняшний день допустим, в том числе переданный как полночь.

Android сохраняет `operationId` и токен отчёта до публикации. При повторе после
потери сети он сначала пытается сохранить черновик, а при ответе
`report_already_published` повторяет публикацию с теми же значениями, чтобы получить
уже созданную неизменяемую версию без дубликата.
При отзыве Android очищает старый ключ и токен, чтобы следующая публикация создала
новую версию, а не попыталась открыть уже отозванную ссылку.
Повтор публикации старого `operationId` после отзыва даёт `409 report_link_revoked`.

Если в отчёте заполнена дата следующего визита, публикация атомарно создаёт `Reminder`
и идемпотентное задание `SEND_REMINDER_SMS`: отправка планируется за семь дней до даты
или сразу, если срок ближе. До отправки напоминание можно отменить. Worker сохраняет
только provider message ID и технический статус `PENDING`/`SENT`/`DELIVERED`/`FAILED`/
`CANCELLED`; текст SMS не попадает в журнал. Для SMS.RU статус доставки опрашивается по
`sms_id`, а в production предпочтителен webhook провайдера для ускорения обновления.

Отзыв отчёта в одной Serializable-транзакции читает последнюю версию, отзывает ссылку,
возвращает отчёт в черновик и визит в ремонт, отменяет ожидающие напоминания этого
визита и переводит их активные задания в `DEAD`. При новой публикации сервер также
отменяет оставшиеся ожидающие напоминания прежних версий, в том числе если новая
дата не задана. История отменённых и уже отправленных записей сохраняется.
Поздний ответ SMS-провайдера не возвращает отменённое напоминание в `SENT`; завершение
worker не возвращает отменённое задание в очередь. Уже переданный провайдеру запрос
невозможно отозвать этой транзакцией: отмена останавливает следующие действия сервиса,
но не обещает отозвать SMS, отправка которой началась раньше отмены.

## Полные списки и сводка мастерской (второй этап)

`GET /v1/visits`, `/v1/customers`, `/v1/reminders` сохраняют массив в ответе для
старых клиентов. Для новых клиентов предусмотрены два режима:

- `?page=1&limit=50` — нумерованная страница для веба;
- `?pagination=cursor&limit=200[&cursor=...]` — последовательная догрузка для Android.

Ответ нового режима: `{ items, total, page, pageSize, hasNext, nextCursor }`.
`total` относится ко всей выборке мастерской с применёнными фильтрами, а не к странице.
Курсор использует неизменяемые `createdAt` и `id` в убывающем порядке; изменение
`updatedAt` между запросами не переносит визит за уже пройденную границу.
Последняя страница содержит `nextCursor: null`. `page` и `pagination=cursor` вместе
не принимаются; повреждённый курсор возвращает 400. Размер страницы — от 1 до 200.
При появлении новых визитов полный новый снимок получают повторным обновлением с первой страницы.
В Android неуспешная догрузка не публикуется как успешный неполный снимок.

`GET /v1/workshop/summary` возвращает `totalVisits`, `activeVisits`, `attentionVisits`,
`visitCounts`, `sent`, `decisions`, `approved`, `approvedValue`, `upcomingReminders`,
`reminderCounts`, `urgentReminders`. Эти показатели агрегируются по всем записям
авторизованной мастерской в согласованном снимке БД. Выполненная согласованная работа
учитывается и в числе отправленных согласований, и в решениях. Стоимость согласованных
работ не является подтверждением фактической оплаты.
`upcomingReminders` содержит только два ближайших `PENDING`; отменённые записи остаются
в журнале, но не показываются как предстоящие. `attention=true` в списке визитов
выбирает активные визиты с запросом звонка клиента.

## Устойчивая идентичность клиента и автомобиля

В PUT визита добавлены необязательные `customerId` и `vehicleId` (UUID).
Android передаёт их после выбора автомобиля в поиске. Сервер проверяет мастерскую,
владельца автомобиля и соответствие телефона выбранному клиенту. Несовпадение даёт
409 `customer_identity_mismatch` или `vehicle_identity_mismatch` и не фиксирует частичные изменения.

Без явного ID сервер ищет клиента по нормализованному телефону, учитывая старые
форматированные номера. Старые записи не объединяются и не удаляются. Несколько
совпадающих клиентов требуют выбора (`409 customer_identity_ambiguous`), кроме сохранения
визита, уже связанного с конкретным клиентом. Поле телефона старой карточки сохраняется,
новые карточки создаются с E.164; снимок телефона визита также нормализован.

При изменении существующего визита сохраняется связанный ID автомобиля. При новой
приёмке автомобиль ищется у выбранного клиента по нормализованному госномеру, независимо
от названия модели. Без номера используется точное название; для переименования такой
машины нужен выбранный `vehicleId`. Неоднозначный номер даёт `409 vehicle_identity_ambiguous`.
Госномер приводится к верхнему регистру без пробелов/дефисов, визуально совпадающие
латинские буквы преобразуются в кириллицу. Поиск также учитывает старые номера с
сочетанием двух алфавитов. Исторические снимки визитов и отчётов не переписываются.

Новые API, Web и Android этого этапа выпускаются согласованно: сначала сервер с
обратно совместимым API, затем Web и новый APK. Старый APK продолжает работать,
но ограничение его загрузки в 200 визитов снимается только обновлением приложения.

## Правила будущего публичного согласования

1. Публичный токен — случайное криптографическое значение не менее 128 бит; в БД хранится только хеш.
2. Решение фиксируется один раз; повтор возвращает уже записанный результат.
3. Фиксируются текст, цена и список медиа, которые видел клиент.
4. Медиа выдаются по короткоживущим presigned URL только из конкретного согласования.
5. Отправка сообщений идёт через очередь с журналом доставки и provider message ID.

## До боевого запуска нужны

- домен и TLS;
- production credentials SMS.RU и согласованное имя/шаблон отправителя;
- выбранный канал доставки и реквизиты провайдера;
- текст сервисного сообщения и политика обработки персональных данных.
