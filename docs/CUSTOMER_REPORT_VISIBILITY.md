# Видимость находок в клиентских отчётах

Внутренние `DRAFT` и `READY_FOR_APPROVAL` не показываются в публичном отчёте и кабинете клиента. Ожидающее клиентского решения `SENT_TO_CUSTOMER` остаётся видимым в кабинете; остальные доступные клиенту статусы сохраняются. Свободный текст, явно введённый мастером в рекомендации отчёта, публикуется как написан.

Перед публикацией Android показывает число не включаемых черновиков. Он сохраняет и передаёт серверу именно увиденные ID; если набор изменился, сервер возвращает `409 private_findings_changed`, и мастер должен обновить визит и проверить отчёт заново. Старые APK не передают такой список и не смогут опубликовать отчёт с черновиками после обновления сервера — это сознательный отказ от молчаливого исключения. Для черновиков автоматические индивидуальные рекомендации и напоминания не создаются. Мастер может явно внести рекомендацию свободным текстом; отдельное структурированное включение с индивидуальным сроком остаётся следующей задачей.

Новые версии отчётов сохраняют неизменяемые связи материалов с находками (`media_manifest`). Публичная проекция скрывает файлы внутренних находок. В старых версиях без таких связей, если есть внутренний черновик, общие несвязанные файлы консервативно не показываются: нельзя подтвердить, что они не относились к черновику. Исходный снимок не переписывается. Фактическое изменение старого отчёта выполняется выпуском новой версии.

Автоматически сформированные строки рекомендаций по внутренним находкам удаляются из клиентской проекции. Если старый снимок повреждён или заголовок черновика содержит разрывы строк и безопасно отделить рекомендацию невозможно, клиентская проекция не показывает блок рекомендаций. Ручное содержимое сохраняется в исходном снимке.

Серверная миграция добавляет nullable JSONB-колонку. Её необходимо применять до запуска нового API; старый API её игнорирует. Android-версия схемы Room повышена с 9 до 11 без удаления данных; на отдельном тестовом пакете TECNO пройдены миграции 5→11 и 9→11 и проверки формы отчёта. Возврат к старому APK со схемой 9 после открытия базы схемой 11 не проверен и может не работать: до обновления рабочих устройств требуется отдельный проверенный план восстановления, не удаляющий свежие данные. Изменения не развёрнуты.

Перед публикацией приложение фиксирует список относящихся к отчёту материалов, проверяет локальную очередь и передаёт список серверу. Сервер сверяет его с известными файлами и не публикует отчёт, пока хотя бы один из них не готов. Повтор после потерянного ответа сначала восстанавливает уже созданную ссылку. Регистрация новых файлов и публикация выполняются в сериализуемых транзакциях; новый файл закрытого визита отклоняется. Старые APK не передают обязательный список файлов и не смогут публиковать отчёт после обновления сервера. Поэтому сервер и Android необходимо выпускать согласованно.

Ограничение: сервер не знает о файлах, которые находятся на другом отключённом устройстве и ещё не зарегистрированы. При последующей синхронизации такой файл не должен молча попадать в уже опубликованный отчёт; требуется организационно завершать синхронизацию всех работающих с визитом устройств до публикации. Полное межустройственное согласование остаётся отдельной задачей.
