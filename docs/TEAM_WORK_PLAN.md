# План разделения работ команды

## Принцип разделения

Команда из двух разработчиков делится по границе продукта, а не по случайным экранам: один владеет рабочим Android-контуром мастера, второй — сервером и клиентским веб-контуром. Единственная общая граница — версионируемый API-контракт.

Это минимизирует конфликты в Git и позволяет параллельно довести локальный цикл на Android и подготовить настоящий сервер.

## Роли

| Участник | Зона ответственности | Не берёт без согласования |
|---|---|---|
| Разработчик A — мобильный | `android/`, локальная БД, камера/аудио, WorkManager, Android UX, HTTP-клиент, тесты устройства | серверную бизнес-логику, публичный веб-интерфейс |
| Разработчик B — backend/web | `server/`, `web/`, PostgreSQL, API, объектное хранилище, публичные ссылки, SMS, серверные тесты и деплой | Room/Compose-экран мастера |
| Владелец продукта | приоритеты, доступ к пилотным мастерским, текст SMS/отчётов, решение по цене и спорным сценариям | ежедневную техническую координацию |
| Codex | декомпозиция задач, реализация по поручению, ревью PR, тест-план, поддержание документов и API-контракта | самостоятельные боевые отправки SMS и изменения инфраструктуры без поручения |

Оба разработчика обязаны участвовать в изменениях `docs/SERVER_CONTRACT.md`: автор предлагает изменение, второй подтверждает его в PR.

## Очередь работ

### Разработчик A: Android

1. Завершить локальный цикл ремонта и сделать его транзакционным.
2. Добавить тесты отчёта, миграций и крайних состояний очереди медиа.
3. Реализовать авторизацию и HTTP-синхронизацию по утверждённому контракту.
4. Подключить реальные статусы согласования и отчёта в Android.
5. Сделать UX-полировку на реальных устройствах и поддержку пилота.

### Разработчик B: server/web

1. Создать каркас `server/` и `web/`, окружения, PostgreSQL и миграции.
2. Реализовать авторизацию, мастерские/сотрудников/устройства, визиты и находки.
3. Реализовать загрузку медиа и контрактные тесты API.
4. Реализовать публичное согласование и клиентские решения.
5. Реализовать отчёты, SMS-очередь, напоминания и кабинет владельца.

## Правила GitHub

- `main` — только рабочие, проверенные изменения; прямой push запрещён.
- Каждая задача имеет GitHub Issue с целью, критериями приёмки и ответственным.
- Для каждой задачи создаётся ветка от актуального `main`: `feat/...`, `fix/...`, `docs/...`; в Codex по умолчанию допустим префикс `codex/`.
- Один pull request решает одну законченную задачу. Автор не сливает свой PR без одного одобрения второго разработчика.
- До merge обязательны: зелёные тесты затронутой части, описание ручной проверки и обновление документации при изменении поведения или API.
- Миграция БД всегда содержит схему, миграцию, тест обновления и план отката.
- Секреты не попадают в Git: только `.env.example`, секреты — в GitHub Secrets/хранилище окружения.

## Именование и владение файлами

| Область | Владелец ревью | Обязательная проверка |
|---|---|---|
| `android/**` | Разработчик A | lint, unit tests, сборка APK; при работе с очередью — ручной offline-сценарий |
| `server/**` | Разработчик B | unit/integration tests, миграции, проверка авторизации |
| `web/**` | Разработчик B | unit/e2e для клиентского решения, мобильная вёрстка |
| `docs/SERVER_CONTRACT.md` | оба | контрактная совместимость Android и API |
| `docs/TECHNICAL_SPECIFICATION.md`, `docs/IMPLEMENTATION_PLAN.md` | владелец продукта + Codex | соответствие цели пилота и отсутствию расползания MVP |

## Первые GitHub Issues

1. **Android: транзакционное завершение ремонта и тесты отчёта** — A.
2. **Server: каркас, PostgreSQL, миграции и авторизация** — B.
3. **Контракт v1: уточнить схемы запросов, ответы и конфликты** — A + B.
4. **Server: идемпотентная синхронизация и медиа-хранилище** — B.
5. **Android: HTTP-транспорт и статус синхронизации** — A.
6. **Web/server: публичное согласование и четыре решения** — B.
7. **Android: реальные решения клиента и завершение отчёта** — A.

Задачи 2 и 3 можно начинать сразу; задачи 4 и 5 начинаются после утверждения контракта; задача 6 открывает проверку основной гипотезы.

## Ритм работы

- Один короткий синк дважды в неделю: что сделано, что блокирует, какие решения нужны владельцу продукта.
- Один демонстрационный сценарий в конце недели: Android → сервер → клиентская страница, когда соответствующие части уже существуют.
- Еженедельно пересматривается backlog: новая функция добавляется только если не сдвигает проверку «находка → решение клиента».
- Критический дефект — потеря данных, неверная цена, доступ к чужой мастерской, повторное SMS или невозможность принять решение — исправляется раньше новой функциональности.

## Definition of Done

Задача завершена только когда выполнены все условия:

1. Код и тесты в отдельном PR.
2. Критерии Issue проверены автором.
3. Есть ревью второго разработчика.
4. Документы и API-контракт обновлены при необходимости.
5. PR можно безопасно откатить; для миграций описан безопасный путь вперёд.
