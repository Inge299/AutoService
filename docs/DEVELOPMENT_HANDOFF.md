# Передача разработки: состояние на 17 сентября 2026

Этот документ — точка входа для второго разработчика. Он описывает фактическое состояние `main` и production, а не только исходный план MVP.

## Коротко

В `main` находится релиз **v0.3.17**. Сквозной сценарий уже работает: мастер авторизуется в Android, создаёт визит и находки, прикладывает фото/видео/голос, отправляет клиенту ссылку, клиент принимает решение на мобильной веб-странице, а мастер после синхронизации видит решение. Клиент по ссылке может создать кабинет и затем войти по паролю либо телефону.

Основной контур пригоден для тестирования с реальными пользователями, но ещё не является готовым коммерческим MVP: требуется стабилизация очереди материалов и доставки ссылок, завершение ремонта/отчётов, эксплуатационные меры и пилотная проверка.

## Репозиторий и роли компонентов

| Каталог | Назначение | Основной владелец |
|---|---|---|
| `android/` | приложение мастера: Compose, Room-кэш, камера/голос, очередь WorkManager | mobile |
| `server/` | Fastify API, Prisma/PostgreSQL, worker, MinIO/S3 | backend |
| `web/` | клиентское согласование, кабинет клиента, веб-кабинет мастерской | backend/web |
| `docs/` | контракт, эксплуатация, решения и план работ | оба разработчика |

Источник истины для бизнес-данных — сервер. Room сохраняет интерфейсный кэш и надёжную очередь медиа на устройстве; он не должен становиться альтернативной бизнес-базой.

## Что реализовано

### Авторизация и доступ

- Мастер: парольный вход и вход по номеру телефона через SMS.RU Callcheck. Сессия состоит из короткого access-token и ротируемого refresh-token; на Android она хранится в Keystore.
- Клиент: публичная ссылка на согласование, создание кабинета с привязкой к этой ссылке, последующий вход паролем или телефоном.
- Публичная ссылка имеет срок жизни, может быть отозвана или заменена. Недействительная/просроченная ссылка показывает понятную страницу вместо технической ошибки.
- Доступ к данным ограничен мастерской; одно решение клиента фиксируется сервером.

### Визиты, находки и согласования

- Создание визитов и находок идёт через HTTPS API; мастер видит реальные серверные состояния.
- Материалы принадлежат конкретной находке, а не списку визита в целом.
- При создании согласования сервер сохраняет версию цены, описания и списка материалов. После отправки нельзя незаметно изменить доказательства или цену.
- Если в находку добавлены подтверждённые материалы до решения, активная ссылка заменяется новой версией, а старая отзывается.
- После всех клиентских решений пересчитывается статус визита; мастер получает результат синхронизацией.

### Медиа и Android

- Поддерживаются фото, короткое видео и голосовая заметка. Медиа сохраняется в закрытом хранилище телефона и имеет состояния локально/в очереди/загружается/готово/повтор.
- WorkManager переживает перезапуск приложения и ждёт сеть. Повтор безопасен благодаря `operationId`, размеру и SHA-256.
- Основной путь — короткоживущий presigned S3 URL. В v0.3.17 добавлен резервный путь: при сетевом сбое прямой загрузки Android передаёт тот же проверенный бинарный файл серверу, который кладёт его в MinIO. Это устранило наблюдавшиеся `broken pipe` и timeout на устройствах.
- На экране мастера есть миниатюры фото, видео и голосовой проигрыватель. Материал можно удалить до отправки на согласование; сервер запрещает удаление после отправки/решения, сохраняя неизменность согласования.

### Веб

- Мобильная страница `/a/:token` показывает находку, цену и все подтверждённые материалы, включая голос.
- Есть страница результата, понятное состояние недоступной ссылки и клиентский кабинет.
- Веб-кабинет мастерской покрывает основной административный сценарий, но не заменяет Android-приложение мастера.

## Известные ограничения и дефекты

Это не «пожелания», а текущая очередь работ. Не следует скрывать их за новой функциональностью.

1. **Галерея мастера визуально показывает лишь две последние миниатюры.** Данные и файлы не теряются: это дефект представления/навигации. Нужны видимый счётчик, возможность открыть весь набор и отсутствие ощущения лимита в две единицы.
2. **Отправка ссылки зависит от готовности материалов.** Сейчас Android создаёт ссылку и открывает системное меню «Поделиться» после подтверждения подходящего набора медиа. Это заставляет мастера ждать и не может самостоятельно отправить сообщение позже.
3. **Фоновая доставка ссылки ещё не реализована.** Системный Android chooser не имеет права автоматически отправлять SMS/мессенджер после ухода мастера. Для этого нужен серверный outbox и разрешённый провайдер доставки с журналом статусов.
4. **Нужно повторно прогнать медиа на реальном телефоне:** несколько фото, видео, голос, плохая сеть, уход приложения в фон, повтор, удаление до согласования и открытие клиентской ссылки после полной синхронизации.
5. **Завершение ремонта, финальный отчёт и напоминания** не доведены до сквозного пилотного сценария.
6. **Эксплуатационная готовность неполна:** нужны резервные копии вне Mia с проверкой восстановления, мониторинг, алерты и политика хранения персональных данных/медиа.

## Целевая модель ссылки и материалов

Направление, согласованное с владельцем продукта: мастер должен иметь возможность нажать «Отправить клиенту» сразу после съёмки, не ожидая сеть. Однако смысл действия должен быть точнее: **«Подготовить согласование и отправить после загрузки»**.

Правильная последовательность:

1. Android фиксирует намерение отправить согласование и выбранные материалы в устойчивой локальной очереди.
2. Очередь догружает все материалы, проверяет их на сервере и создаёт неизменяемую approval-версию только когда список готов.
3. Сервер ставит доставку ссылки в outbox и отправляет её через выбранный канал (например, SMS). Он хранит попытки, ответ провайдера и статус доставки.
4. Android показывает мастеру понятные статусы: «материалы загружаются», «ссылка подготовлена», «отправлено», «не удалось отправить — повторить». Мастер может продолжать работу сразу после первого шага.

Нельзя создавать клиенту ссылку с «пустой рамкой» вместо незагруженного доказательства в той же approval-версии: это создаёт риск, что клиент примет цену до получения доказательств. Если нужно отправить без медиа, это должно быть отдельным явным сценарием — согласование **по описанию без материалов** с соответствующим текстом для клиента.

## Production на Mia

Production не должен запускаться из старой пустой папки `/opt/AutoService`. Воспроизводимая структура:

```text
/opt/autoservice/
  .env                         # API/БД/S3/SMS секреты, не в Git
  current -> releases/vX.Y.Z   # API-версия релиза
  web/
    deploy.env                 # web-секреты, не в Git
    current -> ../releases/vX.Y.Z
  releases/vX.Y.Z/             # чистый clone точного git-тега
```

Работающий релиз разворачивается только из Git-тега, а не копированием рабочей директории. API и web запускаются двумя compose-проектами: `autoservice` и `web`. Подробные команды, проверка и восстановление — в [SERVER_OPERATIONS.md](SERVER_OPERATIONS.md).

После каждого production-деплоя обязательно проверить:

```bash
curl --fail --silent --show-error http://127.0.0.1:8080/health/live
curl --fail --silent --show-error http://127.0.0.1:8080/health/ready
```

Не выводить содержимое `/opt/autoservice/.env`, `web/deploy.env`, токены, ключи S3 или данные клиентов в терминал, Issue, PR и логи CI.

## Инженерные правила

- `main` содержит только проверенные изменения. Работа — из свежей ветки `feat/...`, `fix/...` или `docs/...` (для Codex допустим `codex/...`) и через PR.
- Один PR решает одну законченную задачу; другой разработчик делает review. Изменение API требует обновления [SERVER_CONTRACT.md](SERVER_CONTRACT.md) и согласования Android/backend.
- До merge обязательны релевантные тесты, ручной сценарий и отсутствие ошибок в `git diff --check`. Не коммитить `.env`, keystore, реальные номера, ключи и логи с токенами.
- Миграция Prisma должна быть версионируемой, совместимой с уже развёрнутой БД и иметь план безопасного движения вперёд. В общей/production-БД запрещён `prisma db push`.
- После merge: дождаться зелёного CI, поставить тег, развернуть ровно этот тег, проверить health и ключевой ручной сценарий. Не развёртывать непроверенную ветку.

## Полезные проверки

```bash
# Android (из android/)
./gradlew lintDebug testDebugUnitTest assembleDebug --no-configuration-cache

# Server (из server/)
npm run typecheck
npm test
npm run build

# Web (из web/)
npm run lint
npm run typecheck
npm run build
```

Набор CI и его точные команды следует считать источником истины, если они отличаются от локального окружения. Физическое Android-устройство обязательно для изменений камеры, WorkManager, медиа и авторизации.

## Первый маршрут для нового разработчика

1. Прочитать этот файл, [SERVER_CONTRACT.md](SERVER_CONTRACT.md), [SERVER_ARCHITECTURE.md](SERVER_ARCHITECTURE.md) и [SERVER_OPERATIONS.md](SERVER_OPERATIONS.md).
2. Проверить чистый `main`, запустить локальные проверки затрагиваемого контура и открыть один сквозной сценарий на тестовом устройстве.
3. Взять первый пункт из [ROADMAP_NEXT.md](ROADMAP_NEXT.md), оформить Issue с критериями приёмки и кратким техническим решением.
4. Согласовать изменения контракта до кода; затем сделать небольшой PR с тестами, ручной проверкой и обновлённой документацией.
