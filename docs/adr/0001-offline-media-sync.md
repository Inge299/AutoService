# ADR-0001: Offline-first хранение и синхронизация медиа

**Статус:** принято для технического spike  
**Дата:** 4 сентября 2026

## Контекст

Мастер должен снять много фото и видео без связи, закрыть приложение или заблокировать телефон. После возвращения сети материалы должны загрузиться без повторной съёмки и без ручного открытия каждого визита.

Сетевой запрос не может считаться первичным сохранением: приложение или ОС могут остановить процесс в любой момент. Поэтому подтверждение действия мастеру выдаётся только после локальной записи файла и метаданных.

## Решение

1. Android-приложение является offline-first.
2. Room — локальный источник истины для очереди и доступных визитов.
3. Фото, видео и аудио сначала записываются как `*.capture` в закрытый каталог приложения.
4. После успешного callback файл атомарно переименовывается, затем вычисляются размер и SHA-256.
5. В локальной базе создаётся запись `MediaAsset` со случайными `id` и `operationId`.
6. Для каждого материала планируется уникальная задача WorkManager.
7. Задание запускается только при наличии сети и отсутствии критического дефицита места.
8. Серверный протокол использует `operationId` как ключ идемпотентности.
9. Сервер подтверждает размер и SHA-256 перед переводом материала в `SYNCED`.
10. Оригинал на телефоне не удаляется до подтверждения сервера.
11. При запуске приложение находит завершённые файлы без строки Room, регистрирует их и заново планирует всю незавершённую очередь.

## Состояния

```text
LOCAL → QUEUED → UPLOADING → SYNCED
                    │
                    ├→ RETRY ───────┘
                    └→ BLOCKED
```

- `LOCAL`: файл сохранён, задача ещё не поставлена;
- `QUEUED`: задача поставлена и ожидает условий;
- `UPLOADING`: выполняется попытка;
- `RETRY`: временная ошибка, запланирован повтор;
- `BLOCKED`: файл отсутствует, повреждён или требует решения пользователя;
- `SYNCED`: сервер подтвердил итоговый объект.

После аварийного завершения `UPLOADING` считается повторяемым состоянием. Повтор безопасен благодаря `operationId` и неизменному ключу объекта.

## Инварианты

- Один `operationId` соответствует ровно одному логическому материалу.
- Состояние `SYNCED` невозможно без серверного подтверждения размера и SHA-256.
- Повтор одной операции не создаёт второй материал.
- Сбой сети не удаляет локальный файл.
- Незавершённый `*.capture` никогда не принимается за готовый материал.
- Сбой между фиксацией файла и записью Room устраняется сверкой каталога при запуске.
- Ошибка одного файла не блокирует остальные элементы очереди.
- Пользователь видит все неподтверждённые элементы.
- `Force stop`, удаление приложения, очистка данных и физическая потеря устройства находятся вне технической гарантии; после следующего ручного запуска очередь восстанавливается, если локальные данные сохранились.

## Spike и production

В spike используется `LocalMirrorUploadTransport`: он копирует данные в отдельный закрытый каталог телефона и моделирует идемпотентный сервер. Это позволяет проверить Room, WorkManager, жизненный цикл приложения и отсутствие дублей до готовности backend.

Перед production transport заменяется на возобновляемый HTTP/multipart-протокол. Контракт `UploadTransport` и состояния базы сохраняются.

## Проверка решения

- съёмка без сети;
- закрытие приложения и блокировка экрана;
- перезагрузка устройства;
- восстановление сети через 5 минут, 1 час и 24 часа;
- повтор одной задачи;
- повреждение локального файла;
- недостаток свободного места;
- 200 фото, 20 видео по 30 секунд и 50 голосовых заметок за одну офлайн-смену;
- ноль потерянных подтверждённо сохранённых материалов и ноль дубликатов.
